# NutriFit Craving Engine

[English](README.md) · [Русский](README.ru.md)

Можно ли использовать одну общую модель и при этом учиться на опыте каждого человека без переобучения полноценной модели под каждого пользователя? Craving Engine исследует такую архитектуру для прогноза пищевых срывов по питанию, сну, активности и истории поведения. Общее представление формирует популяционный прогноз; отдельная личная память обновляется, когда приходит обратная связь пользователя.

**Текущая стадия: V10 завершён; преимущество LIF и STDP перед простой личной памятью не подтверждено.** Проверены 35 конфигураций, 8 зафиксированных вариантов и 8 контролируемых сценариев на трёх новых seeds. При смене режима первые улучшения после одного-двух ответов появились и у обычной памяти; уникальное преимущество спайков не установлено. [Полный отчёт V10](docs/results-v10.ru.md) · [Протокол](docs/protocol-v10.ru.md).

Самостоятельный V9 также воспроизведён 7 октября 2026 года: основные метрики всех шести вариантов совпали с архивом точно. Его анатомический кандидат по-прежнему не прошёл допуск. Все выводы относятся к синтетическим данным.

## Цель и критерий успеха

Долгосрочная цель — заранее предупреждать о пищевых срывах при приемлемом числе ложных предупреждений и небольшом состоянии на пользователя. Желаемая полнота — около **94% событий срыва**, а не 94% точности. Совместно с приемлемой нагрузкой ложных предупреждений эта цель не достигнута. Это исследовательский ориентир, а не подтверждённая характеристика продукта.

V9 проверял более узкую гипотезу: может ли обученное на общей когорте представление mushroom body (MB, грибовидное тело) с личной онлайн-памятью превзойти GBDT и простую скалярную персональную поправку настолько, чтобы оправдать новый слепой тест? Для допуска требовались улучшения recall и Youden J, контроль FPR, отсутствие ухудшения Brier, ограничение индивидуальных падений AUC и лучший охват при двух предупреждениях за скользящие семь дней. Точные условия — в [протоколе](docs/protocol-v9.ru.md).

В качестве анатомического ограничения взят фрагмент ALPN → клетки Кеньона из [MaleCNS v1.0](https://male-cns.janelia.org/): 164 связанных ALPN, 2 019 KC и 11 301 взвешенное ребро. Признаки человека подключаются через искусственный адаптер. Это эксперимент с разреженным представлением; функциональная симуляция мозга мухи здесь не реализована. Полезность самой анатомии тоже требует доказательства.

## Что мы попробовали

Все истории синтетические: 60 пользователей для обучения, 20 для калибровки и 40 для development, по 180 ежедневных решений и 94 наблюдаемых признака. Для обучения использованы 8 136 сообщённых исходов из 10 800 решений. Обратная связь поступает с пропусками и задержкой 20 часов по заданным правилам симуляции. Отсутствие ответа не считается отрицательным исходом.

Обучены две популяционные MB-модели: с анатомическим графом и с перемешанными связями при сохранении степеней. Использованы логистические readout и sigmoid-калибровка с разделением пользователей по folds. Для обеих моделей сохранены прогнозы до и после личной памяти. Контролями были фиксированный GBDT и GBDT со скалярной личной поправкой. Наблюдаемые обучающие строки и folds совпадают, но мощности моделей не выровнены. MB выдаёт самостоятельный прогноз, без поправки к вероятности GBDT.

Личная память учится хронологически на уже поступившей обратной связи. Полные синтетические метки оценщика используются для отчёта и выбора порогов на calibration, но не для обучения общей модели или памяти. Пороги заморожены до оценки development. Development-пользователи уже изучались в предыдущих исследованиях: это не слепой holdout.

## Полученный результат

Ниже — показатели исходного V9, точно воспроизведённые самостоятельной версией 7 октября 2026 года. Для каждой модели порог выбирался по максимальному macro recall при macro FPR ≤ 20% на calibration. Простым baseline на calibration выбран **scalar**, единственным кандидатом заранее назначен **anatomical_personal**. Кандидат должен был пройти критерии относительно и scalar, и обычного GBDT.

| Модель | Macro recall ↑ | Macro FPR ↓ | Macro AUC ↑ | Macro Brier ↓ |
| --- | ---: | ---: | ---: | ---: |
| GBDT | 39,65% | 15,40% | 0,7391 | 0,1732 |
| GBDT + скалярная память | 39,51% | 15,12% | 0,7362 | 0,1709 |
| Анатомический MB | 43,24% | 19,70% | 0,7307 | 0,1820 |
| Анатомический MB + личная память | 42,77% | 19,59% | 0,7280 | 0,1780 |
| MB с перемешанными связями | 38,01% | 14,13% | 0,7330 | 0,1776 |
| MB с перемешанными связями + личная память | 37,94% | 14,29% | 0,7306 | 0,1751 |

Recall — доля обнаруженных событий срыва. FPR — доля ошибочно отмеченных решений среди решений без срыва. Macro даёт одинаковый вес каждому подходящему для метрики пользователю. Brier измеряет ошибку вероятностей; Youden J = recall − FPR. Recall и J не являются accuracy. Пороги у моделей разные, поэтому строки не сравнивают модели при одинаковом FPR на development.

- **Относительно GBDT:** кандидат прибавил 3,12 процентного пункта recall при росте FPR на 4,19 пункта. J и AUC снизились, Brier ухудшился. У 20 из 40 пользователей AUC снизилась более чем на 0,01.
- **Личная память внутри анатомического MB:** macro Brier улучшился с 0,1820 до 0,1780, но macro recall и macro AUC снизились. Pooled AUC выросла; эти способы агрегирования отвечают на разные вопросы о ранжировании. Уменьшение ошибки вероятностей не подтвердило улучшение обнаружения срывов или полезности предупреждений.
- **При двух предупреждениях за скользящие семь дней:** кандидат поймал 992 события с 175 ложными предупреждениями; GBDT — 968 с 148. Добавились 24 пойманных события и 27 ложных предупреждений. Это суммарные счётчики, их нельзя смешивать с macro-процентами.
- **На чувствительном пороге:** кандидат получил 93,96% macro recall при 85,49% macro FPR. При лимите двух предупреждений охват составил лишь 29,90% событий. Само повышение чувствительности продуктовую задачу не решило.

Точные значения, парные интервалы и выдержка для чувствительного порога доступны в [результатах](docs/results-v9.ru.md).

## Что подтверждено и что остаётся гипотезой

Исходный эксперимент показал техническую возможность обучить самостоятельный MB-прогноз без GBDT и обновлять личное состояние по задержанной наблюдаемой обратной связи. На этой синтетике личная память также уменьшила Brier относительно собственного популяционного прогноза анатомического MB.

Общее преимущество выбранного кандидата **не подтверждено**. Не установлены полезность именно биологической анатомии, перенос на реальных людей, предотвращение срывов и измеренный бюджет памяти или производительности на миллион пользователей. Результат не отвергает любую личную память или разреженное представление. Следующий этап — выяснить, какие компоненты и предположения ограничили этот вариант, прежде чем переходить к независимому подтверждению.

**Бюджет личного состояния:** в текущем MB три массива по 2 020 значений float64 — всего 48 480 байт (47,34 КиБ) числовых буферов. Дополнительно хранятся ожидающие снимки, история гейта, идентификаторы событий и метаданные. Это только числовые буферы. В V10 отдельно измерен полный JSON checkpoint: для LIF+rSTDP после 180 дней — 68 108–93 397 байт; память процесса и сжатое хранилище не измерены. Полное состояние на 16 КиБ пока не достигнуто. Подробности — в [разборе памяти](docs/personal-state-budget.ru.md).

## С чего начать участнику

1. Начните с [результатов V10](docs/results-v10.ru.md) и [протокола V10](docs/protocol-v10.ru.md); предыдущие [результаты V9](docs/results-v9.ru.md) сохранены. Для обсуждения достаточно исследовательского вопроса с конкретной метрикой и предложенным контролем.
2. Если интересует воспроизведение, используйте маршрут ниже и сохраните сведения об ошибках установки или исполнения. Нужен новый каталог для каждой попытки. Повтор на другой платформе полезен для проверки переносимости.
3. Выберите один вопрос из [плана исследований](docs/research-roadmap.ru.md): сначала вклад личной памяти относительно простых поправок, затем анатомия относительно сопоставимых разреженных контролей, далее reporting и политика предупреждений. До реализации опишите сравнение и критерий успеха.
4. Улучшения на включённых development-данных считайте поисковыми. Для независимого подтверждения нужны новые, ранее не использованные пользователи и зафиксированный протокол. V10 добавляет отдельный генератор контролируемых задач адаптации; он не заменяет реалистичные данные о питании.

Порядок отчётов и участия — в [CONTRIBUTING.md](CONTRIBUTING.ru.md). Полезны и ограниченный отрицательный эксперимент, и отчёт о воспроизведении, и аргументированный методический разбор.

## Маршрут воспроизведения

Запуск V9 из исходников проверен. Набор данных хранится в репозитории, а не в Python wheel. Workflow передачи прав остаётся отдельно непроверенным.

```bash
git clone https://github.com/nutrifit-health/craving-engine.git
cd craving-engine
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
python -m research_v9.experiment --output-dir runs/v9-first --workers 1
```

Каждой попытке нужен новый каталог. Runner обучает два MB-семейства и сравнивает их с сохранёнными прогнозами GBDT. Он не генерирует данные заново, не переобучает GBDT и не открывает свежий holdout. `--workers 2` включает два отдельных процесса. Модели, checkpoints и журналы прогнозов занимают дополнительное место.

[Исходное окружение](original-environment.json) фиксирует исторические версии. [Окружение повторного запуска](results/v10/run-20261007/environment.json) и [результат сравнения](results/v10/verification/v9-reproduction-comparison.json) фиксируют проверенную комбинацию зависимостей. Это не проверка всех версий, разрешённых диапазонами `pyproject.toml`.

Runner загружает pickle только из собственного этапа обучения. Hash подтверждает согласованность артефакта, но не доверие к чужому pickle; не подменяйте модели скачанными файлами.

Все исследовательские и авторские материалы собраны в [оглавлении документации](docs/README.ru.md).
