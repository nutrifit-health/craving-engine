# Персональное состояние: размер по исходному коду, а не измеренный размер хранилища

[English version](personal-state-budget.md)

Текущая реализация V9 **не** подтверждает, что полное состояние одного пользователя занимает 16 KiB. Часто используемый пример из 4 096 значений float32 описывает один гипотетический вектор. В V9 отличаются размерность, dtype и структура состояния.

## Числовые буферы в текущем анатомическом варианте и варианте с перестроенными связями

`FixedContextRepresentation.encode()` в `research_v8/context_representation.py` добавляет якорную координату к представлению графа из 2 019 KC, получая 2 020 координат. `score_records()` в `research_v8/replay.py` передаёт эту размерность кодированного представления в `EncodedMemory`.

`EncodedMemory.__init__()` в `research_v8/memory.py` создаёт три массива:

```python
self.fast = np.zeros(dimension)
self.slow = np.zeros(dimension)
self.exposure = np.zeros(dimension)
```

dtype не указан; [NumPy определяет float64 как тип по умолчанию](https://numpy.org/doc/stable/reference/generated/numpy.zeros.html). При восстановлении также используется `np.asarray(..., dtype=float)`. Поэтому для трёх числовых буферов требуется:

```text
3 массива × 2 020 значений × 8 байт = 48 480 байт = 47.34375 KiB
```

Это расчёт по исходному коду и зафиксированным размерностям графа, а не измеренный объём памяти процесса или размер сериализованного checkpoint. Он не включает накладные расходы массивов/объектов Python, временную память вычислений и другое пользовательское состояние. Расчёт относится к одному персональному варианту MB; исследовательские запуски оценивают варианты отдельно.

## Необходимо и другое состояние

Текущий checkpoint также включает:

- `pending`: разреженные снимки на момент принятия решения, необходимые при поступлении задержанной обратной связи;
- `observations`: недавнюю историю пар «прогноз/исход», используемую механизмом допуска персональной коррекции для каждого пользователя, с настроенным окном в 60 дней;
- `seen`: идентификаторы событий для предотвращения дубликатов; текущая реализация сохраняет их без ограничения размера;
- `clock`, идентификатор представления, конфигурацию и метаданные формата.

V9 использует `head_mode=off`, поэтому глобальный выходной слой не копируется в память каждого пользователя. Три пользовательских массива изначально заполнены нулями; вероятность, полученная обученной популяционной моделью, вычисляется отдельно и передаётся в `predict()`.

`export_state()` преобразует векторы в списки и записывает JSON. В архиве checkpoint хранятся со сжатием gzip. Ни длина JSON, ни размер сжатых данных не равны сумме байтов числовых буферов; они зависят от значений и накопленной истории. При подготовке публичной версии полные измерения памяти или хранилища не проводились.

## Что потребуется для цели в 16 KiB

Ниже приведены бюджеты числовых буферов для гипотетических форматов, а не реализованные оптимизации или результаты оценки качества:

| Три массива по 2 020 значений | Байт в числовых буферах | KiB в числовых буферах |
| --- | ---: | ---: |
| Текущий float64 | 48 480 | 47.34375 |
| Предлагаемый float32 | 24 240 | 23.671875 |
| Предлагаемый float16 | 12 120 | 11.8359375 |

Один лишь переход на float32 всё равно превысит 16 KiB ещё до учёта другого состояния. Формат float16 мог бы уменьшить числовую часть до размера ниже этой цели, но оставил бы 4 264 байта из бюджета в 16 384 байта на всё остальное состояние, если цель охватывает полную запись пользователя. Текущая коллекция `seen` без ограничения размера не позволяет гарантировать фиксированный бюджет на весь срок эксплуатации.

Сначала определите цель: числовые параметры, сжатая запись в постоянном хранилище или полное состояние в оперативной памяти. Затем предлагаемый эксперимент сможет сравнить уменьшение размерности, квантование хранимых данных или вычислений и хранение событий/истории с ограниченным размером. Изменения точности требуют оценки затухания, обновлений, вероятностей, порогов и допуска; меньшие типы данных не доказывают сохранение качества. Не меняйте незаметно сохранённую реализацию V9 ради соответствия числу из статьи.

Для статьи обоснованная формулировка такова: **текущий вариант MB содержит около 47.34 KiB персональных числовых буферов, помимо вспомогательного состояния переменного размера; бюджет персонального состояния в 16 KiB остаётся открытой целью оптимизации.** Пропускная способность для миллиона пользователей и общий объём хранения остаются неизмеренными.

## Измерение в V10

7 октября 2026 года для LIF+rSTDP на прежних V9 development-историях измерены 48 480 байт трёх числовых буферов и 68 108–93 397 байт полного JSON checkpoint после 180 дней. Полный JSON включает ожидающие eligibility, историю гейта, seen и метаданные; это не память процесса и не gzip. [Измерения по пользователям](../results/v10/run-20261007/development_costs.json) · [Отчёт V10](results-v10.ru.md). Число 16 КиБ остаётся неподтверждённым для полного состояния.
